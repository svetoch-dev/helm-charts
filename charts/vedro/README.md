# Vedro

This chart composes two upstream OCI charts from
`oci://ghcr.io/svetoch-dev/charts`:

| Upstream chart | Pinned version | Values alias |
| --- | --- | --- |
| `vedro-controller` | `0.1.0` | `vedro-controller` |
| `vedro` | `0.1.0` | `vedro-resources` |

Both dependencies are disabled by default. Enable either or both. The wrapper
keeps optional nested `probes` and `prometheus-rules` disabled: otherwise the
current dependency composition renders empty monitoring resources.

The controller uses the upstream service-account defaults unless overridden.
With `controller.serviceAccount.create: false`, the named Kubernetes service
account must already exist. Cloud credentials and its GSA mapping are managed
by infrastructure, outside this chart.

## Argo CD

Add these entries to the environment's existing `env.yaml` maps:

```yaml
chart_apps:
  vedro:
    enabled: true
    namespace: vedro
crds:
  enabled: true
  operators:
    vedro:
      enabled: true
```

Put stack values in `environments/<env>/vedro/values.yaml` under the configured
GitOps environment directory. The environment chart supplies `global.*`.

Vedro CRDs must be established before syncing custom resources. Argo CD
Applications generated by this repository use `skipCrds: true`; their CRDs come
from `crds/vedro`. The published controller chart also bundles CRDs for consumers
outside this App-of-Apps setup. Keep the separate CRD snapshot aligned when
updating the pinned upstream charts.

## Application dependencies

An application can depend directly on the upstream `vedro` resource chart using
alias `vedro-resources`; see the [repository README](../../README.md#vedro-charts).
It can reference a shared ProviderConfig and define only its own principals and
buckets. ProviderConfig is cluster scoped; other Vedro resources use the release
namespace unless a namespace is explicitly supplied.

The stack chart defaults `providers.primary` to cloud type, project/folder ID and
region from `global.env.cloud.name`, `id` and `location.region`, using
`WorkloadIdentity`. Its policy permits only the release namespace and bucket
names beginning with `<release>-`; managed principal names are denied until
their patterns are explicitly configured. Referenced principals follow the CRD
defaults. All provider fields can be overridden in environment values.

ProviderConfig is cluster scoped: only one release may own `primary`. Override
its `name` and resource references for an independent provider, as in the example
below, or set `vedro-resources.providers: null` to use an existing provider.
Each bucket must still supply its provider and location. Applications depending
directly on the upstream resource chart do not inherit this wrapper's defaults.

## Local validation

Save the final YAML example below as `/tmp/vedro-values.yaml`, replace the sample
GCP project, and run from the repository root:

```sh
helm dependency build charts/vedro
helm lint charts/vedro -f /tmp/vedro-values.yaml
helm template vedro-demo charts/vedro --namespace vedro -f /tmp/vedro-values.yaml
```

These commands do not create cluster or cloud resources. Dependency archives
are generated locally and ignored, as for other stack charts; `Chart.lock` is
committed. The example renders one controller Deployment plus its RBAC, one
ProviderConfig, two CloudPrincipals, two CloudPrincipalAuths, two Buckets, and
three BucketAccess resources.

## Upstream 0.1.0 limitations

This wrapper does not carry local copies or patches of upstream templates.
When upgrading, verify the upstream fixes and re-render consumer values.

- Always set `principals.*.managed.name`; the documented fallback is not
  implemented in this release.
- `Reference` principals of kind `AllUsers` without a `reference` object fail
  during rendering.
- Equal principal names in different namespaces can produce identical
  BucketAccess names for the same bucket and access level.
- Use a literal `method: StaticCredentials` for static provider credentials;
  upstream tests the raw method before rendering the Secret reference.

The example below avoids these cases.

## Example: two buckets and two service accounts

This is a disposable GCP example for release `vedro-demo` in namespace `vedro`.
Replace `example-project` with your project. Bucket names will be
`vedro-demo-data` and `vedro-demo-backups`; they must be available globally.
Generated GSA names must meet GCP's 6–30 character limit when changing the release
name.

Prerequisites: GKE Workload Identity is configured; KSA `vedro/vedrosa` already
maps to the controller GSA; KSAs `vedro/demo-writer` and `vedro/demo-reader` already
exist. The controller needs cloud permissions to manage buckets, create service
accounts, set bucket access, and manage the requested Workload Identity bindings.

The chart creates GSAs `vedro-demo-writer` and `vedro-demo-reader`, and asks Vedro
to map the two application KSAs to them. The writer receives ObjectWriter on
`data` and ObjectAdmin on `backups`; the reader receives ObjectReader on `data`.
These access levels are passed to Vedro as BucketAccess resources.

`deletionPolicy: Delete` requests deletion of the test buckets and managed GSAs
when their custom resources are removed. Use `Retain` for resources that must
survive removal. During cleanup, keep the controller and ProviderConfig available
until the managed resources have finished deleting.

```yaml
global:
  env:
    cloud:
      name: gcp
      id: example-project
      location:
        region: europe-west1

vedro-controller:
  enabled: true
  controller:
    serviceAccount:
      create: false
      name: vedrosa

vedro-resources:
  enabled: true
  providers:
    primary:
      # Override the default name primary to avoid sharing this example's provider.
      name: "{{ .Release.Name }}"
      # Cloud settings, WorkloadIdentity, namespace and bucket policy use defaults.
      usagePolicy:
        principalPolicy:
          allowedKinds: [ServiceAccount]
          allowedNamePatterns: ["^{{ .Release.Name }}-.*$"]
          allowReferences: false

  principals:
    writer:
      provider: "{{ .Release.Name }}"
      kind: ServiceAccount
      type: Managed
      managed:
        name: "{{ .Release.Name }}-writer"
        deletionPolicy: Delete
      auth:
        method: WorkloadIdentity
        workloadIdentity:
          serviceAccountRef:
            name: demo-writer
    reader:
      provider: "{{ .Release.Name }}"
      kind: ServiceAccount
      type: Managed
      managed:
        name: "{{ .Release.Name }}-reader"
        deletionPolicy: Delete
      auth:
        method: WorkloadIdentity
        workloadIdentity:
          serviceAccountRef:
            name: demo-reader

  buckets:
    data:
      provider: "{{ .Release.Name }}"
      location: "{{ .Values.global.env.cloud.location.region }}"
      prefixReleaseName: true
      deletionPolicy: Delete
      versioning:
        enabled: true
      writers:
        - name: writer
      readers:
        - name: reader
    backups:
      provider: "{{ .Release.Name }}"
      location: "{{ .Values.global.env.cloud.location.region }}"
      prefixReleaseName: true
      deletionPolicy: Delete
      lifecycle:
        rules:
          - name: expire-backups
            action: Delete
            ageDays: 30
      objAdmins:
        - name: writer
```
